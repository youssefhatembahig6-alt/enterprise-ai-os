# Phase 1 Data Model: NileTech Public Website

This feature adds **one** table. Everything else it displays already exists, generated by feature
001 and read here without modification.

## 1. Read-only entities (existing)

All are tenant-owned, carry `company_id`, and sit under the Row-Level Security policy migration
`0002` applied to every tenant table. The public surface reads them with the tenant fixed in
server code (FR-009a) — the RLS policy is the backstop, not the filter.

| Entity | Table | Fields the site reads | Fields it must never expose |
|---|---|---|---|
| Service | `services` | `name`, `summary`, `description`, `display_order` | `id`, `company_id` |
| Public Product | `public_products` | `name`, `tagline`, `description`, `display_order` | `id`, `company_id` |
| Leadership Profile | `leadership_profiles` | `public_title`, `bio`, `display_order`, plus the person's `full_name` via `user_id` | **`user_id`** — an internal identifier of a real employee row; also everything else on `users` |
| News Item | `news_items` | `headline`, `body`, `published_on` | `id`, `company_id` |
| Vacancy | `vacancies` | `title`, `description`, `posted_on`, `is_open`, department `name`, office `city`/`country` | `id`, `company_id`, `department_id`, `office_id` |
| Office | `offices` | `city`, `country`, `address`, `is_headquarters` | `id`, `company_id`, `code` |

**Derived, not stored**: each vacancy and news item gets a slug computed at read time (research
R5). It is not persisted, so this feature adds no column to a seeded table and does not move
feature 001's fingerprints.

**Joins the public reads perform**:

- `leadership_profiles → users` for the person's display name. This is the single place where a public response touches the `users` table, and it selects exactly one column from it.
- `vacancies → departments` and `vacancies → offices` for the department name and office location.

Both joins stay inside the fixed tenant scope; neither can widen it.

**Ordering** (FR-008): `display_order` ascending for services, products, and leadership;
`published_on` descending then headline ascending for news, so ties are deterministic rather than
database-order dependent.

## 2. New entity: Contact Submission

A message left by an anonymous visitor. The only thing this feature writes.

**Table**: `contact_submissions`

| Column | Type | Constraint | Notes |
|---|---|---|---|
| `id` | UUID | primary key | Generated at insert — runtime data, not derived from a natural key like seeded rows |
| `company_id` | UUID | **NOT NULL**, FK → `companies.id` | Fixed server-side to NileTech; never taken from the request |
| `sender_name` | text | NOT NULL, 1–120 chars | |
| `sender_email` | text | NOT NULL, 3–254 chars, format-checked | Bound matches FR-019 and `ck_contact_submissions_sender_email_length` |
| `subject` | text | NOT NULL, 1–150 chars | |
| `message` | text | NOT NULL, 1–4000 chars | Stored verbatim; never interpreted as markup (FR-024) |
| `content_hash` | text | NOT NULL, 64 chars | SHA-256 over the normalized fields — the duplicate-suppression key (research R10) |
| `submitted_at` | timestamptz | NOT NULL | Wall clock. This is runtime data; the pinned reference date does not apply |
| `created_at` / `updated_at` | timestamptz | NOT NULL | Consistent with every other table |

**Constraints**

- `company_id` non-nullable, so the structural audit from feature 001 (`test_tenant_columns`) accepts it as a tenant-owned table rather than flagging it.
- Length bounds enforced as check constraints **and** in the Pydantic model, because FR-020 makes the server the control and a database constraint is the last one standing.
- A partial unique index on `(company_id, content_hash)` covering a recent window is **not** used — see below.

**Duplicate suppression**: implemented as a query-then-insert inside one transaction, not as a
unique constraint. A permanent uniqueness constraint on `content_hash` would refuse a genuine
second enquiry months later from someone who wrote the same short message ("Please call me"),
which is a real message being silently rejected. The window makes the rule "the same message
twice in quick succession is one intent", which is what the edge case describes.

**Row-Level Security**: migration `0003` **enables** RLS on this table with the same
`tenant_isolation` policy shape as every other tenant table. It deliberately does **not**
`FORCE` it, matching migration `0002` — PostgreSQL exempts a table's owner from RLS, and that
exemption is what lets `eaios_owner` run migrations, seed both tenants, and delete aged rows in
the FR-024b retention purge. Forcing RLS here would break all three at once. (`SELECT
relforcerowsecurity FROM pg_class WHERE relname = 'contact_submissions'` returns `f`; this
paragraph said "enables and forces" until a convergence pass compared it to the database.)

Feature 001's `test_every_tenant_table_has_a_policy` derives its table list from
`tenant_tables()`, so this table joins that list automatically and the existing test will fail
if the policy is missing.

**Readability**: never exposed by any public endpoint (FR-023b). The public API can write here and
cannot read here — the router declares no read path for it at all, so the absence is structural
rather than a filter someone could relax.

## 3. Interaction with feature 001's guarantees

Three integration points, each covered in research R8 and each with a test:

| Concern | Why it matters | Change |
|---|---|---|
| **Dataset fingerprint** | A stored submission would alter the fingerprint and fail `verify` | Add `contact_submissions` to the exclusion list; record it in `docs/determinism.md` as FR-015a requires |
| **Reset** | `reset_all` claims to destroy all state | Add the table to the truncation set |
| **Seed pre-flight** | `inspect_stores` iterates `INSERT_ORDER`, which lists seeded tables only — a submission before seeding would leave the environment dirty and invisible | Count this table in the emptiness check |
| **Reset, again** | The FR-024d/FR-047b rate-limit counters are Redis keys under `eaios:ratelimit:*`, which the per-tenant `cache_namespace` scan never matched — so `reset` left them for up to an hour while announcing it destroys every cache entry | Clear `rate_limit_namespace()` in `reset_all`; the pattern lives in `eaios_core.keys` so the writer and the cleaner read the same one |

The third is the subtle one: without it, `seed` would run against a database that is not empty
and believe it was, which is exactly the state feature 001's FR-014 exists to refuse.

## 4. Validation rules

From FR-019 through FR-024, applied server-side first:

| Field | Rule | Message intent |
|---|---|---|
| `sender_name` | required, 1–120 chars after trimming | names the field |
| `sender_email` | required, parseable address, ≤254 chars | names the field and what is expected |
| `subject` | required, 1–150 chars | names the field |
| `message` | required, 1–4000 chars | names the field and the limit |
| whole form | not an exact duplicate of a recent submission | reported as success, not as an error — the visitor's intent was satisfied by the first one |

Every failure returns a field-addressed error so the interface can attach it to the right control
(FR-021), and the response carries no internal detail.

## 5. What this feature adds beyond the table above

Later convergence phases added two pieces of state that this section previously — and
wrongly — said the feature introduced none of. Both are listed here because an
operator auditing this system's state surfaces should find them in one place.

| State | Where | Durability | Why |
|---|---|---|---|
| `contact_submissions` | PostgreSQL | Durable, 90-day retention (FR-024b) | The one thing the public site writes |
| Rate-limit counters | Redis, `eaios:ratelimit:*` | **Ephemeral** — one-hour expiry, cleared by `reset` | Bounds the anonymous write paths (FR-024d, FR-047b) |
| `eaios.retention.purge_expired_submissions` | Celery beat, daily at 03:15 UTC | Standing schedule | Deletes submissions past the retention window (FR-024b) — the project's first scheduled job |

## 6. What this feature still does not add

- No new object-storage keys or vector entries.
- No change to any seeded table, generator, or committed fingerprint.
- No `users`, `roles`, or `permissions` change — those belong to the authorization feature.
