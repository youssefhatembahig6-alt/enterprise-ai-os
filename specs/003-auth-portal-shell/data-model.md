# Phase 1 Data Model: Authentication, Request-Time Authorization, and Employee Portal Shell

**Feature**: `003-auth-portal-shell` | **Date**: 2026-08-05

Two new tables, one new pure-Python type family, and a set of additions to existing
records. Nothing in the generated dataset changes — that is the property SC-014 measures.

---

## 1. New persisted entities

Both are **tenant-owned** and therefore carry `company_id`, inherit `TenantMixin`, and
receive an RLS policy in the same migration that creates them. Neither is generated by the
seed, so neither enters the dataset fingerprint.

### 1.1 `user_credentials`

The stored, non-recoverable verifier for one user's sign-in (spec Key Entities:
*Credential*).

| Column | Type | Null | Notes |
|--------|------|------|-------|
| `id` | `uuid` PK | no | `uuid_pk()`, supplied by the writer |
| `company_id` | `uuid` FK → `companies.id` | no | `TenantMixin`, indexed |
| `user_id` | `uuid` FK → `users.id` `ON DELETE CASCADE` | no | **unique** — one credential per user |
| `password_hash` | `varchar(255)` | no | Argon2id encoded string; carries its own salt and parameters (research R1) |
| `created_at` / `updated_at` | `timestamptz` | no | `TimestampMixin`, wall clock — this is runtime state, not dataset content |

**Constraints**: `UniqueConstraint("user_id")`.

**Never**: returned by any endpoint, written to a log, or written to an audit entry
(FR-018). A test asserts `password_hash` appears in no serialiser and no log record.

**Why its own table rather than `users.password_hash`**: the existing column stays and
stays unused — see research R5 for why dropping it is rejected (it would move both
committed fingerprints). Keeping the credential separate gives it its own lifecycle: the
seed writes users, a later command writes credentials, and a reset clears both
independently.

### 1.2 `sessions`

A time-bounded grant of access to one user (spec Key Entities: *Session*). Server-side
state is what makes FR-007's sign-out real rather than cosmetic.

| Column | Type | Null | Notes |
|--------|------|------|-------|
| `id` | `uuid` PK | no | The `sid` claim in the token |
| `company_id` | `uuid` FK → `companies.id` | no | `TenantMixin`, indexed |
| `user_id` | `uuid` FK → `users.id` `ON DELETE CASCADE` | no | indexed with `company_id` |
| `issued_at` | `timestamptz` | no | sign-in time |
| `absolute_expires_at` | `timestamptz` | no | `issued_at + 8h` (FR-005); never moved |
| `last_seen_at` | `timestamptz` | no | advanced on each accepted request; drives the 30-minute idle bound |
| `ended_at` | `timestamptz` | yes | non-null once ended |
| `ended_reason` | `varchar(16)` | yes | `SIGN_OUT` \| `IDLE` \| `ABSOLUTE`; null while active |

**Constraints**:
`CheckConstraint("absolute_expires_at > issued_at")`,
`CheckConstraint("ended_reason IN ('SIGN_OUT','IDLE','ABSOLUTE')")`,
`CheckConstraint("(ended_at IS NULL) = (ended_reason IS NULL)")` — the two either both say
the session ended or both say it did not; one without the other is a state no code should
have to interpret.

**Index**: `(company_id, user_id, ended_at)` — the shape of "this user's live sessions".

**Validity, evaluated in this order on every protected request** (research R10):

1. `ended_at IS NULL` — else refuse as unauthenticated, reason `SESSION_ENDED`
2. `now() < absolute_expires_at` — else end it with `ABSOLUTE`, refuse
3. `now() - last_seen_at < 30 minutes` — else end it with `IDLE`, refuse
4. advance `last_seen_at`

Two separate bounds rather than one moving expiry: a single "expires at" pushed forward on
activity silently discards the absolute cap, which is the only bound that limits how long
a stolen credential stays useful.

### 1.3 Migration and lifecycle obligations

- **Migration `0004_authentication.py`**, reversible. Creates both tables, enables
  `ROW LEVEL SECURITY`, creates the `tenant_isolation` policy matching migration 0002's
  form, and grants `SELECT, INSERT, UPDATE` on both to `eaios_app`. `DELETE` is withheld,
  matching the existing posture; ending a session is an `UPDATE`.
- **`POST_BASELINE_TABLES` must gain both names.** Migration 0001 builds the schema from
  `Base.metadata`, which is read at migration time — a model not listed there is created
  by 0001 *and* by 0004, and a fresh `alembic upgrade head` fails with *relation already
  exists* while every already-migrated database keeps working. This is written down in
  `packages/core/src/eaios_core/models/__init__.py:82-94` because it has already happened
  once.
- **Reset and emptiness**: both names must be added to
  `RUNTIME_TABLES` in `scripts/seed/src/eaios_seed/loaders/stores.py:53`, which is
  currently `("contact_submissions",)`. That one constant feeds both `reset_all`'s
  `TRUNCATE` and the emptiness pre-flight — and the pre-flight iterates `INSERT_ORDER`,
  which lists *seeded* tables only, so a table missing from `RUNTIME_TABLES` leaves rows
  the pre-flight cannot see and `seed` proceeds against a dirty database. The comment above
  that constant says so, because it has already been the bug once.
- Credentials must therefore be re-provisioned after a reset (FR-002a), and the reset
  output must say so — a reset that leaves a working portal broken with no message is the
  shape of failure this project keeps finding.
- **Fingerprint**: neither is generated, so neither contributes rows to `dataset.rows` and
  neither enters the fingerprint. A test asserts that writing credentials and creating
  sessions leaves the fingerprint byte-identical (SC-014).
- **Retention**: ended sessions are runtime rows with no personal content beyond a user
  reference. The 90-day purge feature 002 added covers `contact_submissions`; extending it
  to ended sessions is **not** in this feature's scope and is recorded as a follow-up.

## 2. The access context (request-scoped, never persisted)

`eaios_core.authz.context.AccessContext` — a frozen dataclass, built once per request from
verified identity, immutable thereafter (FR-008, FR-009).

| Field | Type | Source |
|-------|------|--------|
| `company_id` | `UUID` | verified token claim, **confirmed against `users.company_id`** |
| `company_slug` | `str` | derived constant, for key builders |
| `user_id` | `UUID` | verified token `sub`, confirmed present and active |
| `session_id` | `UUID` | verified token `sid`, confirmed live |
| `department_id` | `UUID` | `users.department_id` |
| `office_id` | `UUID` | `users.office_id` |
| `country` | `str` | `users.country` |
| `employment_type` | `str` | `users.employment_type` |
| `manager_id` | `UUID \| None` | `users.manager_id` — who they report to |
| `direct_report_ids` | `frozenset[UUID]` | `users` where `manager_id = user_id` — who reports to them |
| `role_names` | `frozenset[str]` | `user_roles` ⋈ `roles`; **for display only** |
| `permission_codes` | `frozenset[str]` | `user_roles` ⋈ `role_permissions` ⋈ `permissions` |

**Derived**:

- `permission_fingerprint: str` — stable digest over `(company_id, sorted(permission_codes))`,
  the value `eaios_core.keys.cache_key` has required since feature 001 and nothing has ever
  produced (research R11).
- `has(code: str) -> bool` — the only sanctioned permission test.
- `manages(user_id: UUID) -> bool` — membership in `direct_report_ids`, one level only.

**Immutability is structural, not conventional**: `@dataclass(frozen=True, slots=True)`
with `frozenset` collections. `role_names` is present for the portal's identity display and
is deliberately *not* consulted by the policy engine — FR-014 forbids checking role names,
and a test asserts the engine module never reads that field.

**Both manager directions are required** (FR-008) and they serve different layers:
`manager_id` answers "whose team am I on", `direct_report_ids` answers "whose records may I
read". Only the second is used by this feature's rules; the first is in the context because
the requirement names it and feature 004's approval routing will need it.

## 3. Policy engine types

`eaios_core.authz` — pure, no I/O (research R6).

### 3.1 Inputs

```
Subject       = AccessContext
Action        = StrEnum: READ
ResourceKind  = StrEnum: HR_PROFILE | HR_COMPENSATION | DIRECT_REPORTS
                       | ACCESS_CONTEXT | SESSION | AUDIT_LOG
ResourceDescriptor (frozen):
    kind             : ResourceKind
    resource_id      : str | None          # the subject user id, for HR kinds
    company_id       : UUID | None         # None means "attribute unavailable"
    owner_id         : UUID | None         # whose record this is
    department_id    : UUID | None
    classification   : Classification | None
    acl_grants       : frozenset[AclGrant] # empty is meaningful; None is not representable
```

`ResourceDescriptor` holds **access attributes only** — never a payload field. A test
asserts the dataclass declares no compensation or profile-content field, so the split in
research R7 is enforced by the type rather than by discipline.

### 3.2 Output

```
Decision (frozen):
    allowed         : bool
    reason          : ReasonCode
    layer           : int | None      # which of the five decided, None when allowed by default-permit
    scope           : Scope           # SELF | TEAM | DEPARTMENT | COMPANY | NONE
    audit_required  : bool            # computed from the sensitive set (FR-017a/b)
    tenant_absent   : bool            # layer 1 fired — answer as not found (FR-021, FR-030)
```

`ReasonCode` (stable strings; they appear in audit entries and are asserted by tests):

| Code | Layer | Meaning |
|------|-------|---------|
| `TENANT_MISMATCH` | 1 | resource belongs to another company → **not found** |
| `PERMISSION_MISSING` | 2 | no required permission code |
| `NOT_IN_REPORTING_LINE` | 3 | not the requester's direct report |
| `ATTRIBUTE_MISMATCH` | 3 | any other ABAC condition failed |
| `ACL_DENIED` | 4 | no resource-level grant |
| `CLASSIFICATION_TOO_HIGH` | 5 | classification exceeds the caller's level |
| `CONTEXT_INCOMPLETE` | — | a required attribute was absent → **deny** (FR-013 default) |
| `ALLOWED_SELF` / `ALLOWED_TEAM` / `ALLOWED_ALL` | — | the allow paths, distinguished so the audit says which rule applied |

`tenant_absent` exists so the API layer cannot accidentally turn a layer-1 refusal into a
403: the router maps `tenant_absent=True` to not-found and every other denial to forbidden
(FR-021, FR-030). A single boolean, decided once, in the engine.

### 3.3 Evaluation order (FR-013)

Fixed, short-circuiting, and asserted by test:

1. **Tenant** — `descriptor.company_id == subject.company_id`. Absent → `CONTEXT_INCOMPLETE`.
2. **RBAC** — the required permission code for `(kind, action)`, from a single table in
   `authz.rules`. Codes only; never role names (FR-014).
3. **ABAC** — ownership and reporting-line conditions.
4. **Resource ACL** — `acl_grants`, for kinds that have them.
5. **Classification** — `descriptor.classification` against the caller's ceiling.

**Default deny**: any required attribute that is `None` produces `CONTEXT_INCOMPLETE` and
`allowed=False`. A parametrised unit test drops each attribute in turn from an otherwise
allowing descriptor and asserts every one of them denies — the version of "fails closed"
that can fail.

### 3.4 The sensitive set (FR-017b)

`eaios_core.authz.sensitivity.is_sensitive(descriptor, subject) -> bool`, the single
definition the spec requires. True for:

1. any `HR_PROFILE` where `descriptor.owner_id != subject.user_id`;
2. any `HR_COMPENSATION`, including the requester's own;
3. any descriptor whose `classification` is above `INTERNAL`;
4. any `AUDIT_LOG` read.

`Decision.audit_required = (not allowed) or is_sensitive(...)` — denials always, sensitive
allows only. Call sites never restate the rule; adding a resource kind is one edit here.

### 3.5 Extension points for feature 004

Declared now, unimplemented, so the boundary does not need redesign:

- `ResourceDescriptor` already carries `classification` and `acl_grants` — the two fields a
  document decision needs.
- `AccessContext.permission_fingerprint` is the cache-key component (Principle III).
- `authz.filters.qdrant_filter(subject) -> Mapping[str, object]` returns the payload filter
  (`company_id`, `department_id`, `country`, `classification`, `allowed_roles`, `owner_id`)
  as a plain mapping. Defined and unit-tested against the context; **no Qdrant client is
  imported and no search runs** — the vector store holds nothing (feature 001 decision D2).

## 4. Additions to existing records

### 4.1 `audit_logs` — new actions

No schema change. `actor_type` is `USER` for every entry below; `actor_user_id` is the
acting user; `company_id` is the **actor's** company (research F3).

| `action` | `resource_type` | `decision` | When |
|----------|-----------------|------------|------|
| `auth.sign_in` | `session` | `ALLOW` | successful sign-in |
| `auth.sign_in_failed` | `credential` | `DENY` | any failed sign-in; `resource_id` is **null** — the attempted email is not recorded |
| `auth.locked_out` | `credential` | `DENY` | either bound reached (FR-007a) |
| `auth.sign_out` | `session` | `ALLOW` | explicit sign-out |
| `auth.session_expired` | `session` | `DENY` | idle or absolute bound enforced |
| `authz.denied` | resource kind | `DENY` | every authorization denial (FR-017) |
| `authz.allowed` | resource kind | `ALLOW` | sensitive allows only (FR-017a) |
| `authz.tenant_value_supplied` | `request` | `DENY` | a tenant/role/permission value appeared in a request and was ignored (FR-010) |

`reason` carries the `ReasonCode` plus a short human clause. `sources` stays `[]` — it is
for retrieval provenance and this feature retrieves nothing.

**`auth.sign_in_failed` records no email on purpose.** An audit table listing every
attempted address is an enumeration surface with a longer memory than the sign-in form,
and it is readable by anyone with `audit:read`. The bound counters key on a digest, so the
operational question ("is one account under attack?") is answerable without the table
holding the list.

### 4.2 The HR profile payload

The response for FR-023 / FR-024, assembled from existing tables after the decision:

| Field | Source | Notes |
|-------|--------|-------|
| `user_id`, `full_name`, `email` | `users` | |
| `department`, `office`, `country`, `employment_type` | `departments`, `offices`, `users` | names, not ids |
| `manager_name` | `users` self-join | null for the one manager-less user per company |
| `job_title`, `hire_date` | `employee_profiles` | |
| `leave_balance` | `leave_balances` | current year, annual type (FR-023) |

**`salary_amount`, `salary_band`, and `currency` are absent from this model entirely.**
They are reachable only through `GET /hr/profiles/{user_id}/compensation`, which requires
`hr:read_all`. That separation is what lets FR-025's denial be proven *before* the query
rather than by filtering the response — the compensation query is a different statement,
and on a denied path it never executes (research R7).

### 4.3 Redis keys

Reusing `RATE_LIMIT_PREFIX` so `reset_all` clears them by pattern (research R8, and the
drift lesson recorded at `packages/core/src/eaios_core/keys.py:30-38`):

| Bucket | Identity | Threshold / window |
|--------|----------|--------------------|
| `login:account` | SHA-256 of the lowercased email, truncated | 5 / 15 min |
| `login:address` | SHA-256 of the client address, truncated | 20 / 15 min |

No plaintext email and no plaintext address is ever a key component, matching the
reasoning already written in `apps/api/src/eaios_api/public/rate_limit.py`.

## 5. What is deliberately absent

| Not modelled | Why |
|--------------|-----|
| Refresh tokens | FR-005 fixes an 8-hour absolute cap and the spec's scope boundary excludes account lifecycle. A refresh token that could extend past the cap would contradict FR-005; one that could not would add a mechanism with no effect. |
| Password reset / registration / MFA | Named out of scope by the spec. |
| A `permissions` cache | This feature reads the permission set per request (FR-004 requires current records). Caching it is a feature-004 concern and needs the fingerprint defined in §2. |
| Any write to business data | The spec states the feature reads only, which is what keeps Principle VII's approval gate out of scope. |
