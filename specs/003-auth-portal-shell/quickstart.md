# Quickstart: Authentication, Request-Time Authorization, and Employee Portal Shell

**Feature**: `003-auth-portal-shell`

How to bring the feature up and how to prove each claim it makes. Every scenario names the
command, the expected result, and — where it matters — **what a false pass would look
like**, because most of the checks here are the kind that pass by having nothing to check.

---

## Prerequisites

Docker Desktop running, `uv` installed, `pnpm` installed. From a clean checkout:

```bash
make up
```

Brings up PostgreSQL, Qdrant, Redis, MinIO, the API, the worker, and the site, waits for
health, and applies migrations through `0004_authentication`.

```bash
make seed
```

Generates the dataset. Fingerprint after this step is the committed known-good value;
`users.password_hash` is NULL for all 240 users, as it has been since feature 001.

```bash
make credentials
```

The new step (FR-002a). Writes one `user_credentials` row per active seeded user, hashed
with Argon2id. Refuses to run unless `ENVIRONMENT=local`. Prints the demo password it
used and the count of rows written.

> On Windows, App Control blocks the virtualenv's `.exe` shims. Run tools as
> `uv run python -m pytest ...` rather than `uv run pytest ...`.

## Scenario 1 — Sign in and read your own record (US1, FR-023)

```bash
make up && make seed && make credentials
```

Open <http://localhost:3000/portal>. Sign in as the seeded engineering employee — the
persona keys are listed in `docs/personas.md`, regenerated by `make docs`.

**Expect**: the portal greets the employee by name and `/portal/profile` shows their own
department, office, manager, employment type, and leave balance. No salary appears
anywhere on the page.

**Then sign out** and reload `/portal/profile`.

**Expect**: returned to sign-in, not an error page.

```bash
uv run python -m pytest tests/integration/test_auth_login.py -m integration -v
```

## Scenario 2 — Sign-out actually ends access (FR-007, SC-002a)

The check that matters is a **replay**, not an observation that the browser stopped
sending the credential.

```bash
uv run python -m pytest tests/security/test_session_lifecycle.py -m security -v
```

**Expect**: the test signs in, keeps the exact token, signs out, then presents that same
token and gets 401.

**A false pass looks like**: asserting that a *new* request without a token is refused.
That proves nothing about revocation — an unauthenticated request was always refused.

## Scenario 3 — A manager sees their team and nobody else (US2, FR-024, SC-003)

```bash
uv run python -m pytest tests/security/test_manager_scope.py -m security -v
```

**Expect**: the seeded engineering manager reads every one of their direct reports, and is
refused (403) for an employee in another department.

**A false pass looks like**: the manager having zero direct reports, making "reads every
report" vacuously true. The test asserts the direct-report set is non-empty **and** the
unrelated-employee set is non-empty before asserting anything about access.

## Scenario 4 — Salary is denied before the query runs (FR-025, FR-036, SC-007)

The blueprint's flagship denial, and the one requirement a response-body assertion cannot
establish.

```bash
uv run python -m pytest tests/security/test_authorize_before_read.py -m security -v
```

**Expect**: a manager requesting a direct report's compensation gets 403, and the
statements recorded for that request contain **no** reference to
`employee_profiles.salary_amount`.

**A false pass looks like**: the recorder capturing nothing at all — every assertion of the
form "the forbidden query did not run" passes when no query ran. The same test asserts the
`hr:read_all` caller's request **does** execute that statement, so the recorder is proven
to be watching.

## Scenario 5 — Zero cross-tenant access (US3, FR-034, SC-004)

```bash
uv run python -m pytest tests/security/test_cross_tenant_authenticated.py -m security -v
```

**Expect**: a Delta Retail identity requesting a NileTech record by identifier receives
**404**, byte-identical to the response for an identifier belonging to nobody — not 403,
which would confirm the record exists (FR-021, FR-030).

**A false pass looks like**: the NileTech identity also reaching nothing, so "zero Delta
records" is true because zero records were reached. The test asserts the NileTech
caller's own reachable set is non-empty in the same run.

## Scenario 6 — Request-supplied tenant, role, and permission are ignored (FR-035, SC-005)

```bash
uv run python -m pytest tests/security/test_request_supplied_claims.py -m security -v
```

**Expect**: the same request, repeated with `?company_id=`, `X-Company-Id:`, a
`company_id` in the body, a `roles` field, and a `permissions` field, returns **the
caller's own data**, unchanged, in every case. Each attempt writes an
`authz.tenant_value_supplied` audit entry.

**A false pass looks like**: asserting the manipulated request returns nothing. A
manipulated request that fails for an unrelated reason also returns nothing. The assertion
is equality with the unmanipulated response.

## Scenario 7 — Sign-in reveals nothing about which accounts exist (FR-022, FR-007a, SC-013)

```bash
uv run python -m pytest tests/security/test_login_enumeration.py -m security -v
```

**Expect**: responses for an unknown email, a known email with a wrong password, an
inactive user, and a locked-out account are identical in status, headers, and body. Six
failures against one account refuse the seventh; twenty-one from one address refuse the
next. No refusal states which bound was reached.

**A false pass looks like**: comparing wall-clock timings and calling them "close enough"
on a loaded runner. The timing property is asserted structurally instead — the test proves
the dummy-hash verification path executes when no user matches, so the work is the same
rather than the measurement being lucky.

---

## Scenario 8 — Session expiry, both bounds (FR-005, SC-002)

```bash
uv run python -m pytest tests/integration/test_session_expiry.py -m integration -v
```

**Expect**: a session idle past 30 minutes is refused and its row shows
`ended_reason = 'IDLE'`. A session kept continuously active past 8 hours is refused with
`ended_reason = 'ABSOLUTE'` — activity renews the idle bound and never the cap.

Time is advanced by writing the session row's timestamps, not by sleeping. A test that
waits eight hours is a test nobody runs.

## Scenario 9 — The audit trail says what happened, and nothing it must not (FR-017, FR-018, SC-006)

```bash
uv run python -m pytest tests/security/test_authz_audit.py -m security -v
```

**Expect**:

- every denial writes one entry with actor, tenant, action, resource type and id, decision,
  reason, and timestamp;
- reading a *direct report's* profile writes an allow entry (sensitive: someone else's HR
  record);
- reading *your own* non-compensation profile writes **nothing** — asserted as a delta of
  zero, in the same test that asserts a sensitive read writes exactly one;
- no entry anywhere contains a password, a token, or a fragment of either.

**A false pass looks like**: asserting `audit_logs` is non-empty. It is never empty — the
seed writes to it. Every assertion here is a before/after delta plus content.

## Scenario 10 — Determinism survives credentials (FR-002a, SC-014)

```bash
make fingerprint          # before
make credentials
make fingerprint          # after — must be byte-identical
make verify
```

**Expect**: the fingerprint is unchanged. It is computed from the in-process generated
rows, not from the database, so a post-seed write cannot move it.

Then the full round trip:

```bash
make reset                # destroys everything, regenerates, re-runs migrations
make credentials          # required again — reset leaves credentials cleared
```

**Expect**: sign-in works again with the same password, and the fingerprint still matches.
The reset output states that credentials must be re-provisioned.


caller who holds it, asserted together.

## Scenario 13 — Contracts have not drifted

```bash
make contracts-check
```

**Expect**: exit 0. The committed TypeScript client is regenerated against the running API
and diffed; drift names the line and exits 1.

Run `make contracts` after any schema change and commit the result. The generated file is
committed on purpose, and `pnpm typecheck` passes against a stale one quite happily.

## The whole thing

```bash
make test && make test-site && make contracts-check
```

Mirrors the CI order. The security suite blocks the change on failure (FR-037) — a
non-zero leakage result is a release blocker, not a triage item.
